[[mongodb-sink-overview]]
== Overview
endif::community[]
The {prodname} MongoDB sink connector captures change event records from Apache Kafka topics and then transforms the records into MongoDB documents that it writes to collections in a specified MongoDB sink database.
For applications that require high scalability and fast data retrieval, propagating change data to a cluster-based MongoDB environment, which uses such features as sharding and replica sets to optimize read operations, can significantly improve retrieval performance.
The connector can process only change events that originate from a {prodname} relational database connector.

[[mongodb-sink-architecture]]
== Architecture and how it works

The {prodname} MongoDB sink connector mirrors the state of tables in a relational source database to collections in a MongoDB database by consuming {prodname} change events from Kafka topics and applying them as document-level operations.

The connector subscribes to Kafka topics that are populated with event messages produced by {prodname} relational database source connectors.
Each event message describes a database operation (insert, update, or delete) in a structured format that captures the details of the event.
The connector transforms incoming change event records into MongoDB document format, and then writes the resulting documents into the target MongoDB collection.

After it receives an event, the connector parses the event payload and determines which MongoDB collection to send it to.
Depending on the event type that is specified in the event payload, the connector then performs one of the following operations in the target collection:

[cols="30%,70%",options="header"]
|===
|Event type in payload|Resulting operation

|INSERT
| Create document

|UPDATE
|Modify document with the specified identifier.

|DELETE
|Remove document with the specified identifier.

|===

The connector uses the MongoDB Java driver to interact with the MongoDB database.

The mapping between topics and MongoDB collections is derived from the connector configuration.
The document key serves as a unique identifier for the document, ensuring that updates, inserts, and deletions are propagated to the correct MongoDB document and collection, and that operations are applied in the correct order.

Through this process of mapping event messages to MongoDB documents, the connector is able to mirror the state of tables in your relational database to collections in a MongoDB database.

[[mongodb-sink-limitations]]
== Limitations

The {prodname} MongoDB sink connector has the following limitations:

Relational database / RDBMS source connectors only::
The MongoDB sink connector can consume only change events that originate from the {prodname} connectors for the following relational databases:

* MariaDB
* MySQL
* Oracle
* PostgreSQL
* SQL Server

+
The connector cannot process change event messages from any other {prodname} connectors, including the {prodname} MongoDB source connector.
ifdef::community[]
The connector supports both standard {prodname} envelope records and flattened records (for example, records processed by the `ExtractNewRecordState` single message transform).
endif::community[]

Schema evolution::
Although the connector can process basic schema changes, advanced schema evolution scenarios might require manual intervention or specific configuration.
Because MongoDB is schemaless, it has only a limited ability to handle schema evolution.

Transaction Support::
The connector processes individual change events in chronological order, based on the order in which operations are committed in the source system.
Although MongoDB supports transactions, the {prodname} MongoDB connector does not provide transactional guarantees across multiple CDC events or across multiple documents within a single sink task.

== Quick Start (using Kafka Connect)

Deploy a basic instance of the MongoDB sink connector for testing.

.Prerequisites

The following components are available and running in your environment:

* Kafka cluster
* Kafka Connect
* A MongoDB instance.
* {prodname} relational database connector
* {prodname} MongoDB connector

.Procedure
. Configure and start a {prodname} source connector, for example, a {prodname} PostgreSQL Connector, to stream changes from a relational database to Kafka.
. Configure and start the {prodname} MongoDB sink connector to consume events that the source connector emits to Kafka, and send them to a MongoDB sink database.
+
The following example provides a minimal configuration for a {prodname} MongoDB sink connector.
Replace the placeholders in the example with the actual values for your environment.
+
[source,json,indent=0,subs="+attributes"]
----

  "name": "mongodb-sink-connector",
  "config": {
    "connector.class": "io.debezium.connector.mongodb.sink.MongoDbSinkConnector",
    "topics.regex": "server1\.inventory\..*",
    "mongodb.connection.string": "mongodb://localhost:27017",
    "sink.database": "debezium"
  }
}
----

ifdef::community[]
.Primary key configuration
[cols="30%a,25%a,45%a",options="header"]
|===
|Property | Default | Description

|[[mongodb-sink-property-primary-key-mode]]<<mongodb-sink-property-primary-key-mode, `+primary.key.mode+`>>
|`none`
|Specifies how the connector resolves the `_id` field of the target MongoDB document from the event.

`none`:: No primary key is derived from the event. The connector generates a unique MongoDB `ObjectId` for each document's `_id` field.
`kafka`:: The connector uses the Kafka coordinates as the document `_id`. The `_id` is composed of the following fields:
* `+__connect_topic+`
* `+__connect_partition+`
* `+__connect_offset+`
`record_key`:: The connector derives the `_id` from the event's record key. If the record key is a struct type, the xref:mongodb-sink-property-primary-key-fields[`primary.key.fields`] property is optional and can restrict the `_id` to a subset of key fields.
`record_value`:: The connector derives the `_id` from the event's value. Set the xref:mongodb-sink-property-primary-key-fields[`primary.key.fields`] property to specify which value fields to use; otherwise all fields are used.
`record_header`:: The connector derives the `_id` from the event's Kafka headers.

[NOTE]
====
When using `primary.key.mode=none` writes are not idempotent, because a new `ObjectId` is generated each time a record is processed.
If the connector retries a record (for example, after a transient network error or a task restart), the re-delivered record produces a new document instead of overwriting the original.
This may result in duplicate documents in the target collection.
If you need exactly-once semantics for keyless data, use `kafka` mode instead.
====

|[[mongodb-sink-property-primary-key-fields]]<<mongodb-sink-property-primary-key-fields, `+primary.key.fields+`>>
|No default
|A comma-separated list of field names to use as the primary key.
The interpretation depends on the xref:mongodb-sink-property-primary-key-mode[`primary.key.mode`] setting:

* When `primary.key.mode` is `record_key`, restricts the `_id` to the specified subset of key fields.
* When `primary.key.mode` is `record_value`, specifies which value fields compose the `_id`.
* When `primary.key.mode` is `record_header`, specifies which header fields compose the `_id`.

|===

[[mongodb-sink-error-handling]]
=== Error handling and dead letter queues

When the connector fails to write a record to the target MongoDB database for a reason that is not transient, for example, because the record has a malformed payload, by default the failure stops the connector task.

The connector can route failing records to the ErrantRecordReporter that the Kafka Connect runtime provides (see link:https://cwiki.apache.org/confluence/display/KAFKA/KIP-610%3A+Error+Reporting+in+Sink+Connectors[KIP-610]).
When a batch fails with a non-transient error, the connector retries the records in the batch one at a time to isolate the failing records, routes only those records to the reporter, and continues to process the remaining records.
Transient failures, such as network errors (`MongoSocketException`), topology changes (`MongoNotPrimaryException`, `MongoNodeIsRecoveringException`), or errors labeled as `RetryableError` by the MongoDB server, are not routed to the reporter; they are propagated to the Kafka Connect framework for retry.

Whether a failing record stops the task or is routed to a dead letter queue is controlled by the standard Kafka Connect error handling options:

.Example dead letter queue configuration
[source,json]
----
{
  "errors.tolerance": "all",
  "errors.deadletterqueue.topic.name": "dlq-topic",
  "errors.deadletterqueue.context.headers.enable": "true"
}
----

When `errors.tolerance` is set to `none` (the default), or when no dead letter queue topic is configured, failing records stop the connector task.

Because a dead letter queue topic can never receive records while `errors.tolerance` is set to `none`, the connector rejects that combination and fails to start with a message that describes how to correct the configuration.

[NOTE]
====
MongoDB bulk write operations are non-transactional by default.
When writing an ordered batch, earlier writes in the batch may have already been committed when a later write fails.
When `primary.key.mode` is set to `record_key`, `kafka`, `record_value`, or `record_header`, the connector uses upsert semantics (`ReplaceOneModel` with `upsert=true`), so replaying the same batch after a partial failure produces the same result — the already-committed writes are simply overwritten with the same values.
When `primary.key.mode` is set to `none`, each write generates a new `ObjectId`, so replaying a batch after a partial failure creates duplicate documents for the already-committed writes.
See xref:mongodb-sink-delivery-semantics[] for details.
====
endif::community[]

== Key field mapping

ifdef::product[]
When the connector processes events, it maps data to specific fields in the target MongoDB document.

* Keys from {prodname} change events, such as Kafka message keys, are mapped to the MongoDB `_id` field by default.
* Values are mapped into MongoDB documents.
* Updates and deletes are resolved based on the key field mapping.

The following example shows an event key in a Kafka topic:
endif::product[]

ifdef::community[]
When the connector processes events, it resolves the MongoDB `_id` field based on the xref:mongodb-sink-property-primary-key-mode[`primary.key.mode`] configuration.

When `primary.key.mode` is set to `none` (the default), the connector generates a unique MongoDB `ObjectId` for each document.

When `primary.key.mode` is set to `record_key`, the connector maps the event's record key to the `_id` field.
For example, the following composite key in a Kafka topic:
endif::community[]

[source,json,indent=0,subs="+attributes"]
----
{
    "userId": 1,
    "orderId": 1
}
----

is mapped to the `_id` field in a MongoDB document as follows:

[source,json,indent=0,subs="+attributes"]
----
{
    "_id": {
        "userId": 1,
        "orderId": 1
    }
}
----

ifdef::community[]
You can restrict which key fields compose the `_id` by setting the xref:mongodb-sink-property-primary-key-fields[`primary.key.fields`] property.
For example, setting `primary.key.fields=userId` produces:

[source,json,indent=0,subs="+attributes"]
----
{
    "_id": {
        "userId": 1
    }
}
----

When `primary.key.mode` is set to `kafka`, the `_id` is derived from the Kafka coordinates of the event:

[source,json,indent=0,subs="+attributes"]
----
{
    "_id": {
        "__connect_topic": "dbserver1.inventory.customers",
        "__connect_partition": 0,
        "__connect_offset": 42
    }
}
----

Values from the event payload are mapped into the MongoDB document fields.
Key fields that are part of the `_id` are excluded from the document body to avoid duplication.

[TIP]
====
`kafka` mode is the recommended setting for sinking keyless data such as log streams, audit events, or transaction records.
Because the `_id` is derived from the Kafka topic, partition, and offset, writes are idempotent: if a record is re-delivered after a transient error or task restart, it overwrites the existing document rather than creating a duplicate.
====

[[mongodb-sink-delivery-semantics]]
== Delivery semantics

Kafka Connect provides at-least-once delivery guarantees: after a transient failure (network error, primary failover) or task restart, records may be re-delivered from the last committed offset.
Whether re-delivery produces duplicates in the target MongoDB collection depends on the xref:mongodb-sink-property-primary-key-mode[`primary.key.mode`] setting.

Idempotent (keyed) modes::
When `primary.key.mode` is set to `record_key`, `kafka`, `record_value`, or `record_header`, the connector derives a deterministic `_id` from the event.
Because the connector writes documents using `ReplaceOneModel` with `upsert=true`, re-delivering the same record overwrites the existing document with the same `_id` — the write is idempotent and no duplicates are created.

Non-idempotent (keyless) mode::
When `primary.key.mode` is set to `none` (the default), the connector generates a random MongoDB `ObjectId` for each write.
A re-delivered record receives a new `ObjectId` and is inserted as a new document, resulting in a duplicate.
+
This applies to any scenario that triggers re-delivery:
+
* A transient MongoDB error (network interruption, primary failover) during a bulk write causes the Kafka Connect framework to restart the task and re-deliver records from the last committed offset.
* A consumer group rebalance when partitions are reassigned across tasks.
* An ordered bulk write that partially succeeds — records written before the failure are re-delivered alongside the failed ones.
+
If your use case requires all records to be preserved without duplicates (for example, sinking log streams, audit events, or financial transactions), set `primary.key.mode` to `kafka`.
The `kafka` mode derives the `_id` from the Kafka topic, partition, and offset, providing a stable, unique identifier that makes writes idempotent while preserving every distinct record.
endif::community[]

[[mongodb-sink-cloudevents]]
== Using CloudEvents with {prodname} MongoDB Sink Connector

The {prodname} MongoDB sink connector can consume records serialized as CloudEvents.
{prodname} can emit change events in CloudEvents format, so that the event payload is encapsulated in a standardized envelope.

When you enable CloudEvents on the source connector, the MongoDB sink connector parses the CloudEvents envelope.

The actual {prodname} event payload is extracted from the data section.

The event is then applied to the target MongoDB collection, following the standard insert, update, or delete semantics.

This process makes it possible to integrate {prodname} with broader event-driven systems while still persisting the resulting events in MongoDB.

.CloudEvents sink options
[cols="30%a,25%a,45%a",options="header"]
|===
|Property | Default | Description

|[[mongodb-sink-property-cloud-events]]<<mongodb-sink-property-cloud-events, `+cloud.events.schema.name.pattern+`>>
| `.*CloudEvents\.Envelope$`
| Regular expression pattern to identify CloudEvents messages by matching the schema name with this pattern.

|===
