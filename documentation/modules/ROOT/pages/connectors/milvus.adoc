The {prodname} Milvus connector captures row-level changes in the collections of a link:https://milvus.io/[Milvus] vector database.
ifdef::community[]
For information about the Milvus versions that are compatible with this connector, see the link:https://debezium.io/releases/[{prodname} release overview].
endif::community[]

Milvus does not expose a change stream through its gRPC API.
Instead, Milvus publishes every write to an internal message queue (MQ) channel before it persists the write.
The {prodname} Milvus connector reads that channel directly, which means that it connects to three parts of a Milvus deployment: the MQ backend, the etcd cluster that stores channel checkpoints, and the Milvus gRPC endpoint.

The first time that the connector connects to a Milvus cluster, it reads a consistent snapshot of the collections that it is configured to capture.
The snapshot is anchored to the channel checkpoint that Milvus records in etcd, so that no change is lost or duplicated when the connector transitions from the snapshot to streaming.
After the snapshot completes, the connector begins to emit change events for inserts and deletes that Milvus commits to the captured collections.
By default, change events for a particular collection go to a Kafka topic that is named after the collection.
Applications and services can then consume change event records from these topics.

// Title: Overview of the {prodname} Milvus connector
[[milvus-overview]]
== Overview

A Milvus cluster writes all data manipulation operations to a set of physical channels (pchannels) on its message queue backend.
Each pchannel multiplexes the traffic of several virtual channels (vchannels); a vchannel belongs to a single collection shard.
Alongside insert and delete messages, Milvus periodically publishes _timetick_ messages that advance the logical clock of each vchannel.

The connector uses these three sources of information:

Message queue backend (Kafka):: The connector subscribes to the pchannel topic that is named by the `milvus.pchannel.name` property, and consumes the raw insert, delete, and timetick messages that Milvus writes to it.

etcd:: Milvus stores the checkpoint of each channel in etcd, as a `guarantee_ts` timestamp and the corresponding offset in the MQ.
The connector reads this checkpoint to anchor the snapshot and to determine the position from which to resume streaming.
Because the Milvus API does not expose checkpoint data, the connector requires direct access to the etcd cluster that backs Milvus.

Milvus gRPC API:: During the snapshot, the connector uses the API to list collections, read their schemas, and query rows.
During streaming, the connector uses the API to resolve the schema of a collection that it has not yet observed in an insert event.

Milvus assigns every operation a timestamp from a Hybrid Logical Clock (HLC), which the Milvus documentation refers to as a TSO.
The high 46 bits of a TSO encode the number of milliseconds that elapsed since the UNIX epoch, and the low 18 bits encode a logical counter that orders operations that occur within the same millisecond.
The connector preserves this value in the `source` block of every event, and uses it to order events across vchannels.

[[how-the-milvus-connector-works]]
== How the connector works

To optimally configure and run a {prodname} Milvus connector, it is helpful to understand how the connector performs snapshots, orders events, and names topics.

// Type: concept
// ModuleID: how-debezium-milvus-connectors-perform-database-snapshots
// Title: How {prodname} Milvus connectors perform database snapshots
[[milvus-snapshots]]
=== Snapshots

When a Milvus connector starts for the first time, it performs an initial snapshot of the collections that it captures.
The connector completes the following steps:

. Reads the etcd checkpoint of the configured pchannel to obtain the `guarantee_ts` timestamp and the MQ offset that corresponds to it.
The connector stores the MQ offset in its offsets so that the streaming phase knows where to resume.

. Retrieves the list of collections in the database that the `milvus.database` property names, and applies the `milvus.collection.include.list` and `milvus.collection.exclude.list` filters.

. Queries every included collection through the Milvus SDK with `consistency_level` set to `Strong` and `guarantee_ts` pinned to the checkpoint timestamp.
Pinning the query to the checkpoint guarantees that the snapshot observes exactly the state of the collection at the point in the change stream from which streaming later resumes.

. Emits each row as a read (`op=r`) event.

. Records `snapshot_completed=true` in the connector offsets and hands off to the streaming phase.

If the etcd checkpoint does not exist, for example, because the Milvus cluster has not yet written to the pchannel, the snapshot completes immediately without emitting rows, and the streaming phase falls back to the latest position in the MQ.

If the connector fails after the snapshot begins but before it completes, the connector starts a new snapshot after it restarts.

The connector does not take a separate schema snapshot.
Milvus collection schemas are resolved dynamically, either from the Milvus metadata API during the snapshot, or from the first insert event that the connector observes during streaming.

.Snapshot modes
The `snapshot.mode` property controls the snapshot behavior:

`initial`:: The connector performs a snapshot when no offsets exist, and then streams changes. This is the default.
`never`:: The connector never performs a snapshot. It begins streaming from the position that its stored offsets specify, or from the latest position in the MQ if no offsets exist.
`when_needed`:: The connector performs a snapshot if no offsets exist, or if the stored offsets refer to a position that is no longer available in the MQ.
`recovery`:: The connector performs a snapshot to rebuild lost or corrupted connector state.

[NOTE]
====
The Milvus connector does not support incremental snapshots, ad hoc snapshots, or blocking snapshots.
====

// Type: concept
// ModuleID: how-debezium-milvus-connectors-stream-change-events
// Title: How {prodname} Milvus connectors stream change events
[[milvus-streaming-changes]]
=== Streaming changes

After the snapshot completes, the connector seeks its MQ consumer to the offset that the etcd checkpoint recorded, and enters the streaming loop.
For each iteration, the connector completes the following steps:

. Polls a batch of raw messages from the pchannel topic.

. Deserializes each message.
Depending on its version, a Milvus cluster uses one of two wire formats for its MQ payloads: a msgpack batch envelope, or a single protobuf message per record.
By default the `milvus.wire.format` property is set to `auto`, which causes the connector to probe the channel and detect the format that the cluster uses.
Because the format is stable for a given cluster, the connector treats a mixed detection as a fatal error.

. Buffers the deserialized events in the timetick ordering engine and updates the per-vchannel timetick watermarks.

. Flushes events whose TSO is behind the _global watermark_, which is the minimum timetick across all active vchannels.
Because no vchannel can subsequently produce an event with a lower TSO, the flushed events are guaranteed to be complete and are released in strict TSO order.

. Dispatches the flushed events to the {prodname} event pipeline, and only afterwards advances the connector offsets with the new MQ position and vchannel watermarks.
Updating offsets after dispatch ensures that the connector never commits an offset for an event that it did not emit.

If a vchannel stops advancing its timetick for longer than the interval that the `milvus.timetick.stall.timeout.ms` property specifies, the connector logs a warning and force-flushes the buffered events rather than stalling indefinitely.
To bound memory use, the ordering engine applies backpressure when the buffer exceeds the limits that the `milvus.buffer.max.events` and `milvus.buffer.max.bytes` properties set.

After a restart, the connector pre-warms the ordering engine with the vchannel watermarks that it stored in its offsets, so that streaming resumes without waiting for a fresh timetick from every vchannel.

A Milvus connector supports a single task and consumes a single pchannel.
If `tasks.max` is set to a value greater than `1`, the connector logs a warning and ignores the value.

[[milvus-topic-names]]
=== Topic names

By default, the Milvus connector writes change events for all of the insert and delete operations in a collection to a single Kafka topic.
The connector names change event topics according to the following format:

_topicPrefix_._databaseName_._collectionName_

The following list provides definitions for the components of the default name:

_topicPrefix_:: The value that the `topic.prefix` configuration property specifies.
_databaseName_:: The Milvus database that contains the collection, as specified by the `milvus.database` property.
_collectionName_:: The name of the Milvus collection in which the operation occurred.

For example, if `topic.prefix` is set to `milvus`, the connector captures the `default` database, and a row is inserted into the `orders` collection, the connector emits the event to the `milvus.default.orders` topic.

To change the topic naming convention, you can configure a custom topic naming strategy.

// Title: Descriptions of {prodname} Milvus connector data change events
[[milvus-events]]
== Data change events

The {prodname} Milvus connector generates a data change event for each row-level insert and delete operation.
Each event contains a key and a value.
The structure of the key and value depends on the collection that was changed.

The connector emits the following operations:

[cols="1,1,3,3",options="header"]
|===
|Operation |`op` |`before` |`after`

|Snapshot read
|`r`
|`null`
|The full row, as it existed when the snapshot ran.

|Insert
|`c`
|`null`
|The full row that was inserted.

|Delete
|`d`
|The primary key of the deleted entity only.
|`null`
|===

Milvus `DeleteRequest` messages carry only the primary keys of the entities that are deleted, and do not carry their prior state.
As a result, the `before` field of a delete event contains a value for the primary key field only; every other field is `null`.

Milvus implements an upsert as a delete followed by an insert.
The connector emits that pair of operations as it observes them on the channel, so it does not emit update (`op=u`) events.

Collection creation and removal are tracked internally, so that the connector can order events correctly, but they are not emitted as schema change events.
The connector does not produce a schema change topic.

[[milvus-change-event-keys]]
=== Change event keys

The key of a change event contains the primary key field of the Milvus collection in which the change occurred.
For a collection named `orders` in the `default` database with an `Int64` primary key field named `id`, and a connector for which `topic.prefix` is set to `milvus`, the key of every change event has the following structure:

[source,json,indent=0]
----
{
  "schema": {
    "type": "struct",
    "name": "milvus.default.orders.Key",
    "optional": false,
    "fields": [
      {
        "name": "id",
        "index": "0",
        "schema": {
          "type": "INT64",
          "optional": "false"
        }
      }
    ]
  },
  "payload": {
    "id": 1004
  }
}
----

[[milvus-change-event-values]]
=== Change event values

The value of a change event uses the standard {prodname} envelope, which contains `before`, `after`, `source`, `op`, and `ts_ms` fields.

.Example: insert event
The following example shows the value of a change event that the connector emits after an entity is inserted into the `orders` collection:

[source,json,indent=0]
----
{
  "payload": {
    "before": null,
    "after": {
      "id": 1004,
      "product": "milk frother",
      "quantity": 2,
      "embedding": [0.12, 0.98, 0.37, 0.51]
    },
    "source": {
      "version": "{debezium-version}",
      "connector": "milvus",
      "name": "milvus",
      "ts_ms": 1754630400000,
      "snapshot": "false",
      "db": "default",
      "collection": "orders",
      "pchannel": "by-dev-rootcoord-dml_0",
      "vchannel": "by-dev-rootcoord-dml_0_449282886501507477v0",
      "tso": 459876543210987654
    },
    "op": "c",
    "ts_ms": 1754630400123
  }
}
----

.Example: delete event
The following example shows the value of a change event that the connector emits after the same entity is deleted.
The `before` field contains the primary key only:

[source,json,indent=0]
----
{
  "payload": {
    "before": {
      "id": 1004,
      "product": null,
      "quantity": null,
      "embedding": null
    },
    "after": null,
    "source": {
      "version": "{debezium-version}",
      "connector": "milvus",
      "name": "milvus",
      "ts_ms": 1754630500000,
      "snapshot": "false",
      "db": "default",
      "collection": "orders",
      "pchannel": "by-dev-rootcoord-dml_0",
      "vchannel": "by-dev-rootcoord-dml_0_449282886501507477v0",
      "tso": 459876543299887654
    },
    "op": "d",
    "ts_ms": 1754630500456
  }
}
----

After a delete event, the connector emits a tombstone event, unless you set the `tombstones.on.delete` property to `false`.

.Descriptions of `source` fields
The `source` block of a Milvus change event contains the following connector-specific fields, in addition to the fields that all {prodname} connectors provide:

[cols="1,4",options="header"]
|===
|Field |Description

|`db`
|The name of the Milvus database that contains the collection.

|`collection`
|The name of the Milvus collection in which the operation occurred.

|`pchannel`
|The name of the Milvus physical channel from which the connector read the event.

|`vchannel`
|The name of the Milvus virtual channel that carried the event. Each vchannel corresponds to a collection shard.

|`tso`
|The raw Milvus HLC timestamp of the operation. The high 46 bits encode milliseconds since the UNIX epoch, and the low 18 bits encode a logical counter. The `ts_ms` field is derived from the physical component of this value.
|===

[[milvus-data-type-mappings]]
== Data type mappings

The following table describes how the connector maps each Milvus data type to a Kafka Connect schema type.

[cols="2,2,3",options="header"]
|===
|Milvus data type |Kafka Connect schema type |Notes

|`Bool`
|`BOOLEAN`
|

|`Int8`, `Int16`
|`INT16`
|

|`Int32`
|`INT32`
|

|`Int64`
|`INT64`
|

|`Float`
|`FLOAT32`
|The mapping depends on the setting of the `decimal.handling.mode` property.

|`Double`
|`FLOAT64`
|The mapping depends on the setting of the `decimal.handling.mode` property.

|`String`, `VarChar`, `Text`
|`STRING`
|

|`JSON`, `Geometry`
|`io.debezium.data.Json`
|A logical type with an underlying type of `STRING`.

|`Array`
|`STRING`
|The array is encoded as a JSON string, so that the element type does not need to be known when the schema is built.

|`FloatVector`
|`io.debezium.data.vector.FloatVector`
|A logical type with an underlying type of `ARRAY` of `FLOAT32`.

|`SparseFloatVector`
|`STRING`
|A JSON encoding of the sparse representation.

|`BinaryVector`, `Int8Vector`, `Float16Vector`, `BFloat16Vector`
|`BYTES`
|

|`ArrayOfVector`, `ArrayOfStruct`
|`BYTES`
|These structures are opaque to the connector; raw bytes is the only lossless representation.
|===

.Floating-point values
Milvus `Float` and `Double` fields are IEEE-754 floating-point values rather than SQL `DECIMAL` or `NUMERIC` values.
For this reason, the Milvus connector sets the default value of the `decimal.handling.mode` property to `double` rather than to `precise`, which is the default for relational connectors.

You can override this default:

`double`:: Emits native `FLOAT32` and `FLOAT64` values. This is the default.
`precise`:: Emits `org.apache.kafka.connect.data.Decimal` values, which have an underlying type of `BYTES`.
`string`:: Emits the values as formatted strings.

[[setting-up-milvus]]
== Setting up Milvus

Before you deploy the connector, configure the Milvus cluster so that the connector can read its change stream.

.Prerequisites

* A Milvus 2.5 or later deployment.
* Java 21 or later on the Kafka Connect worker.

.Procedure

. Configure Milvus to use Kafka as its message queue backend.
In the Milvus configuration file, set the following properties:
+
[source,yaml,indent=0]
----
mq:
  type: kafka
kafka:
  brokerList: kafka:19092
----
+
[IMPORTANT]
====
The connector supports Kafka only.
Milvus deployments that are backed by Pulsar or RocksMQ are not supported.
====

. Note the value of the `etcd.rootPath` property in the Milvus configuration, which defaults to `by-dev`.
You supply this value to the connector through the `milvus.etcd.root.path` property, so that the connector can locate the channel checkpoints.

. Determine the name of the pchannel that the connector consumes.
The default is `by-dev-rootcoord-dml_0`, which follows the pattern `_etcdRootPath_-rootcoord-dml__n__`, where _n_ is the channel index.
The `rootCoord.dmlChannelNum` property controls how many pchannels a Milvus cluster creates.
+
[NOTE]
====
Because a connector instance consumes a single pchannel, deploy one connector for each pchannel that you want to capture.
====

. Verify that the Kafka Connect worker can reach the Milvus gRPC endpoint, the Kafka cluster that Milvus uses as its MQ backend, and the etcd cluster that backs Milvus.

. If the Milvus deployment requires authentication, create a user for the connector and supply its credentials through the `milvus.token` property.

[[milvus-deployment]]
== Deployment

To deploy a {prodname} Milvus connector, you install the connector archive on a Kafka Connect server, configure the connector, and start the Kafka Connect service.

.Prerequisites

* <<setting-up-milvus,Milvus is set up>> to run a {prodname} connector.
* Apache Kafka and Kafka Connect are installed.

.Procedure

. Download the {prodname} Milvus connector plug-in archive.
. Extract the files into your Kafka Connect environment.
. Add the directory that contains the connector files to the Kafka Connect `plugin.path`.
. Restart the Kafka Connect process to pick up the new JAR files.

[[milvus-example-configuration]]
=== Connector configuration example

The following example shows the configuration of a connector that captures the collections whose names begin with `orders` from the `default` database of a Milvus instance:

[source,json,indent=0]
----
{
  "name": "milvus-connector",  // <1>
  "config": {
    "connector.class": "io.debezium.connector.milvus.MilvusConnector",  // <2>
    "topic.prefix": "milvus",  // <3>
    "milvus.uri": "http://localhost:19530",  // <4>
    "milvus.database": "default",
    "milvus.etcd.endpoints": "http://localhost:2379",  // <5>
    "milvus.etcd.root.path": "by-dev",
    "milvus.kafka.bootstrap.servers": "localhost:9092",  // <6>
    "milvus.pchannel.name": "by-dev-rootcoord-dml_0",  // <7>
    "milvus.collection.include.list": "orders.*",  // <8>
    "snapshot.mode": "initial"
  }
}
----
<1> The name of the connector.
<2> The name of the connector class. Always specify this value for a Milvus connector.
<3> The prefix of the Kafka topics to which the connector writes change events.
<4> The gRPC endpoint of the Milvus cluster.
<5> The endpoints and root path of the etcd cluster in which Milvus stores its channel checkpoints.
<6> The Kafka cluster that the Milvus deployment uses as its message queue backend. This is typically distinct from the Kafka cluster that Kafka Connect writes change events to.
<7> The Milvus physical channel that the connector consumes.
<8> A comma-separated list of literal names or regular expressions that match the collections to capture.

You can send this configuration to a running Kafka Connect service with the `POST` command of the Kafka Connect REST API.

[NOTE]
====
The Milvus connector rejects the `heartbeat.action.query` property.
The generic action-query feature requires a JDBC connection on which to run the query, and Milvus is not a relational data source.
Interval-based heartbeats, which you configure with the `heartbeat.interval.ms` and `heartbeat.topics.prefix` properties, are fully supported.
====

[[milvus-monitoring]]
== Monitoring

The {prodname} Milvus connector provides the snapshot and streaming metrics that are common to all {prodname} connectors, and a small number of Milvus-specific metrics.

The connector exposes snapshot metrics through the following JMX object name:

`debezium.milvus:type=connector-metrics,context=snapshot,server=_<topic.prefix>_`

.Milvus-specific snapshot metrics
[cols="2,1,4",options="header"]
|===
|Attribute |Type |Description

|`GuaranteeTso`
|`long`
|The etcd checkpoint TSO to which the snapshot is anchored, or `0` if no checkpoint was available.

|`SnapshotStartTs`
|`long`
|The time, in milliseconds since the epoch, at which the snapshot phase started, or `0` if the snapshot has not started.
|===

The connector exposes streaming metrics through the following JMX object name:

`debezium.milvus:type=connector-metrics,context=streaming,server=_<topic.prefix>_`

.Milvus-specific streaming metrics
[cols="2,1,4",options="header"]
|===
|Attribute |Type |Description

|`PositionResolved`
|`boolean`
|`true` after the connector resolves and assigns the start offset of its MQ consumer for the current streaming run.
Unlike the `Connected` attribute, which becomes `true` as soon as the streaming loop starts, this attribute distinguishes the state in which streaming has started from the state in which the consumer position is known and events are observed from that point onward.

|`MilliSecondsBehindSource`
|`long`
|The replication lag, in milliseconds. The connector computes this value as the difference between the current time and the physical component of the global timetick watermark.
|===

[[milvus-limitations]]
== Limitations

The connector has the following limitations:

* The connector supports a single task, and consumes a single pchannel for each connector instance.
To capture a Milvus cluster that uses multiple pchannels, deploy one connector for each channel.
* The connector supports Kafka only as the Milvus message queue backend.
Deployments that are backed by Pulsar or RocksMQ are not supported.
* Delete events carry a `before` image that contains the primary key only, because Milvus does not publish the prior state of a deleted entity.
* The connector does not emit update (`op=u`) events.
Milvus implements upserts as a delete followed by an insert, and the connector emits that pair of operations.
* The connector does not emit schema change events, and does not produce a schema change topic.
* The connector does not support incremental snapshots, ad hoc snapshots, or blocking snapshots.
* The connector does not support the `heartbeat.action.query` property.
