The {prodname} SQLite connector captures row-level changes in the tables of a link:https://www.sqlite.org/[SQLite] database file.
ifdef::community[]
For information about the SQLite versions that are compatible with this connector, see the link:https://debezium.io/releases/[{prodname} release overview].
endif::community[]

SQLite is an embedded database that stores an entire database in a single file, and it exposes no replication log or change stream that an external process can follow.
Instead, the connector captures changes with SQL triggers.
For each table that it captures, the connector installs `AFTER INSERT`, `AFTER UPDATE`, and `AFTER DELETE` triggers.
Every trigger writes one row that describes the change into an internal table named `_debezium_cdc_log`, in commit order.

The first time that the connector starts, it reads a consistent snapshot of the tables that it is configured to capture.
After the snapshot completes, the connector streams changes by reading the new rows that the triggers append to the CDC log table.
By default, change events for a particular table go to a Kafka topic that is named after the table.
Applications and services can then consume change event records from these topics.

[[sqlite-overview]]
== Overview

Because SQLite has no server process and no built-in change stream, the connector runs against the database file directly and derives a change stream from SQL triggers.

The connector opens the same database file that the application writes to, and it opens the file in link:https://www.sqlite.org/wal.html[write-ahead logging (WAL)] mode.
WAL mode lets the connector read the database in short transactions while application writers continue to commit, so capture does not block the application and the application does not block capture.

For each captured table, the connector installs three triggers, one each for `INSERT`, `UPDATE`, and `DELETE`.
Every trigger appends a single row to the `_debezium_cdc_log` table within the same transaction as the change that fired it, so a change and its log row commit together, or not at all.
The CDC log table has the following structure:

[cols="2,2,5",options="header"]
|===
|Column |Type |Description

|`change_id`
|`INTEGER PRIMARY KEY AUTOINCREMENT`
|A monotonically increasing identifier that SQLite assigns in commit order. It is the position that the connector streams from and stores in its offsets.

|`table_name`
|`TEXT`
|The name of the table in which the change occurred.

|`operation`
|`TEXT`
|The kind of change: `c` for an insert, `u` for an update, and `d` for a delete.

|`old_row_data`
|`TEXT`
|A JSON object with the row's values before the change. It is `null` for an insert.

|`new_row_data`
|`TEXT`
|A JSON object with the row's values after the change. It is `null` for a delete.

|`committed_at`
|`INTEGER`
|The time, in milliseconds since the UNIX epoch, at which the change was recorded.
|===

Because the triggers write to the log in the same transaction as the change, the `change_id` order is the commit order, and the connector emits change events in that order.
The connector reads the log in small batches, emits a change event for each row, and advances its offset to the `change_id` of the last row that it processed.
So that the log does not grow without bound, the connector periodically deletes the rows whose changes {prodname} has already committed downstream.

A SQLite connector uses a single task, and each connector instance captures a single database file.

[[how-the-sqlite-connector-works]]
== How the connector works

To optimally configure and run a {prodname} SQLite connector, it is helpful to understand how the connector performs snapshots, streams changes, and names topics.

[[sqlite-snapshots]]
=== Snapshots

When a SQLite connector starts for the first time, it performs an initial snapshot of the tables that it captures.
The connector completes the following steps:

. Switches the database file to WAL journal mode, and creates the `_debezium_cdc_log` table if it does not already exist.

. Installs the capture triggers on each table that it captures.
From this point on, SQLite logs every insert, update, and delete to the CDC log table with a `change_id`, so that no change that occurs during or after the snapshot is lost.

. Opens a read transaction on the WAL, which provides a consistent view of the database without locking the tables or blocking application writers.

. Reads the highest `change_id` in the CDC log within that same view, and stores it in the connector offsets as the position from which streaming later resumes.
Because the connector reads the mark and the table data from one consistent view, any change that is committed after the mark is left for the streaming phase, with no gap and no duplicate.

. Reads every row of each captured table, and emits it as a read (`op=r`) event.
The connector also emits one schema change event per table.

. Records that the snapshot is complete in the connector offsets, and hands off to the streaming phase, which resumes from the stored `change_id`.

.Snapshot modes
The `snapshot.mode` property controls the snapshot behavior:

`initial`:: The connector performs a snapshot when no offsets exist, and then streams changes. This is the default.
`always`:: The connector performs a snapshot every time that it starts, and then streams changes.
`no_data`:: The connector does not snapshot data. It installs the capture triggers if they are missing, and begins streaming from the current position of the CDC log.
`initial_only`:: The connector performs a snapshot when no offsets exist, and then stops without streaming.

[NOTE]
====
The SQLite connector does not support incremental snapshots, ad hoc snapshots, or blocking snapshots.
====

[[sqlite-streaming-changes]]
=== Streaming changes

After the snapshot completes, the connector begins to poll the CDC log table, and streams the rows that the triggers append to it.
For each poll, the connector completes the following steps:

. Reconciles the capture triggers if the database schema has changed since the previous poll, so that a schema change is picked up before the connector reads the next batch.

. Deletes already-committed rows from the CDC log once enough of them have accumulated, so that the log does not grow without bound.

. Reads a batch of rows whose `change_id` is greater than the stored offset, up to the limit that the `cdc.log.batch.size` property sets.

. Emits a change event for each row, in `change_id` order, and advances the offset to the `change_id` of the last row that it emits.

If a poll returns no rows, the connector pauses for the poll interval before it polls again.
The connector reads each batch in a short, autocommitted transaction, so that SQLite can checkpoint the WAL between polls.

Because the triggers write to the CDC log in the same transaction as the change that fired them, the `change_id` order is the commit order, and the connector emits change events in that order.

A SQLite connector supports a single task, because SQLite allows a single writer.
If you set `tasks.max` to a value greater than `1`, the connector logs a warning and uses a single task.

[[sqlite-topic-names]]
=== Topic names

By default, the SQLite connector writes all of the change events for a table to a single Kafka topic.
The connector names change event topics according to the following format:

_topicPrefix_._tableName_

The following list provides definitions for the components of the default name:

_topicPrefix_:: The value that the `topic.prefix` configuration property specifies.
_tableName_:: The name of the table in which the operation occurred.

SQLite has no catalog or schema, so the table name is the only qualifier between the prefix and the name of the topic.
For example, if `topic.prefix` is set to `sqlite`, and a row is inserted into the `orders` table, the connector emits the event to the `sqlite.orders` topic.

To change the topic naming convention, you can configure a custom topic naming strategy.

[[sqlite-events]]
== Data change events

The {prodname} SQLite connector generates a data change event for each row-level insert, update, and delete operation.
Each event contains a key and a value.
The structure of the key and the value depends on the table that was changed.

The connector emits the following operations:

[cols="1,1,3,3",options="header"]
|===
|Operation |`op` |`before` |`after`

|Snapshot read
|`r`
|`null`
|The full row, as it existed when the snapshot ran.

|Insert
|`c`
|`null`
|The full row that was inserted.

|Update
|`u`
|The full row, as it existed before the update.
|The full row, as it exists after the update.

|Delete
|`d`
|The full row, as it existed before the delete.
|`null`
|===

Because the capture triggers record the complete `OLD` and `NEW` row for every change, update and delete events carry a full before image, not only the primary key.

[[sqlite-change-event-keys]]
=== Change event keys

The key of a change event contains the primary key of the table in which the change occurred.
For a table named `orders` whose primary key is an `INTEGER` column named `id`, and a connector for which `topic.prefix` is set to `sqlite`, the key of every change event has the following structure:

[source,json,indent=0]
----
{
  "schema": {
    "type": "struct",
    "name": "sqlite.orders.Key",
    "optional": false,
    "fields": [
      {
        "field": "id",
        "type": "int64",
        "optional": false
      }
    ]
  },
  "payload": {
    "id": 1004
  }
}
----

[[sqlite-change-event-values]]
=== Change event values

The value of a change event uses the standard {prodname} envelope, which contains `before`, `after`, `source`, `op`, and `ts_ms` fields.

.Example: create event
The following example shows the value of a change event that the connector emits after a row is inserted into the `orders` table:

[source,json,indent=0]
----
{
  "payload": {
    "before": null,
    "after": {
      "id": 1004,
      "name": "milk frother",
      "quantity": 2
    },
    "source": {
      "version": "{debezium-version}",
      "connector": "sqlite",
      "name": "sqlite",
      "ts_ms": 1754630400000,
      "snapshot": "false",
      "db": "sqlite",
      "table": "orders",
      "change_id": 42
    },
    "op": "c",
    "ts_ms": 1754630400123
  }
}
----

.Example: update event
The following example shows an update to the same row.
The `before` field holds the row as it existed before the change, and the `after` field holds the row as it exists after the change:

[source,json,indent=0]
----
{
  "payload": {
    "before": {
      "id": 1004,
      "name": "milk frother",
      "quantity": 2
    },
    "after": {
      "id": 1004,
      "name": "milk frother",
      "quantity": 5
    },
    "source": {
      "version": "{debezium-version}",
      "connector": "sqlite",
      "name": "sqlite",
      "ts_ms": 1754630500000,
      "snapshot": "false",
      "db": "sqlite",
      "table": "orders",
      "change_id": 43
    },
    "op": "u",
    "ts_ms": 1754630500456
  }
}
----

.Example: delete event
The following example shows the deletion of the same row.
The `before` field holds the row as it existed before the delete, and the `after` field is `null`:

[source,json,indent=0]
----
{
  "payload": {
    "before": {
      "id": 1004,
      "name": "milk frother",
      "quantity": 5
    },
    "after": null,
    "source": {
      "version": "{debezium-version}",
      "connector": "sqlite",
      "name": "sqlite",
      "ts_ms": 1754630600000,
      "snapshot": "false",
      "db": "sqlite",
      "table": "orders",
      "change_id": 44
    },
    "op": "d",
    "ts_ms": 1754630600789
  }
}
----

After a delete event, the connector emits a tombstone event, unless you set the `tombstones.on.delete` property to `false`.

.Descriptions of `source` fields
The `source` block of a SQLite change event contains the following connector-specific fields, in addition to the fields that all {prodname} connectors provide:

[cols="1,4",options="header"]
|===
|Field |Description

|`table`
|The name of the table in which the operation occurred.

|`change_id`
|The identifier that the connector assigned to the change in the CDC log. It increases monotonically in commit order, and is the position from which the connector resumes streaming.
|===
